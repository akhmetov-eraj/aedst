| Session lives in **httpOnly cookies** set only by the web server (OIDC Route Handlers `app/api/auth/{login,callback}`, the logout Server Action, `proxy.ts`, `/api/rpc`); page JavaScript never sees a token. Sign-in is **OpenID Connect Authorization Code + PKCE as a backend-for-frontend** against the IdP (ZITADEL default) with `oauth4webapi` 3.8.8: state, nonce and PKCE verifier live in a short-lived AES-256-GCM-sealed httpOnly pre-auth cookie (`OIDC_STATE_SECRET`), the callback validates state/nonce/ID token and writes access + refresh + ID token cookies; logout clears cookies, revokes the refresh token and sends the browser to the IdP's `end_session_endpoint` (`id_token_hint`, `post_logout_redirect_uri`) when advertised. The web app no longer calls `AuthService` and has no password forms. The browser talks only to same-origin `/api/rpc` (a backend-for-frontend proxy that attaches the bearer token and refreshes once on 401); apps/server is reached only from server code (`API_BASE_URL`) | Accepted | An XSS could exfiltrate `localStorage` tokens; a cookie session can only be *ridden*, not stolen. Also removes CORS, the cross-origin `connect-src` and every credential form (identity stays the IdP's job, ADR-0001) | A second first-party client needs direct API access with its own token (keep the BFF for the browser) |
| Refresh = the OIDC `refresh_token` grant against the discovered token endpoint (`oauth4webapi`, `shared/lib/auth/refresh-session.ts`). Refresh tokens rotate, so refreshes stay single-flight per token **per process** with a 10 s reuse window. Across replicas (no shared store in web) the first `invalid_grant` for a token is `stale`: that request is treated as signed out (page redirect / 401) but the refresh cookie is **not** cleared (only a dead access cookie is dropped on a 401), because another replica probably rotated the token and its Set-Cookie must not be overwritten; the same token still refused after 15 s is final and clears the session. `invalid_token`/`unauthorized_client` end the session at once, any other failure (IdP outage, network) does not. The ID token from the login and from refresh responses is signature-verified with `oauth4webapi` (`validateApplicationLevelSignature`, issuer `jwks_uri`, RS256/ES256/EdDSA allow-list, `none`/HMAC refused), no new dependency; a response without a new refresh token keeps the old one. Roles come from the access token via `AUTH_ROLES_CLAIM` (`urn:zitadel:iam:org:project:roles` for ZITADEL: object keyed by role, `{orgId: domain}` values) with the optional `AUTH_ROLES_ORG` filter, mirroring the server's `rolesFromToken` | Accepted | Parallel requests must not race a one-time token into a spurious sign-out; the UI must read roles exactly as the server does | **Guaranteed:** no race inside one replica; a losing replica never logs the user out by itself. **Not guaranteed (needs sticky routing, e.g. by session cookie or client IP, for multi-replica web):** two replicas refreshing the same token still burn it, and if the winner's Set-Cookie never reaches the browser (cancelled navigation) the session is lost after 15 s; ZITADEL does **not** revoke the token family on reuse (verified 2026-10-08, v4.19.4: replaying a spent refresh token gets 400 `Errors.OIDCSession.RefreshTokenInvalid` and the newer token still refreshes afterwards), so a losing replica does not kill the winner's token; the refresh response does carry a new `id_token`. ZITADEL documents no reuse-grace setting (only access/ID token lifetime and refresh token expiration/idle expiration), so there is none to configure; revisit if ZITADEL adds one (or Valkey is approved for web, to share the refresh result), or the server roles rules change |
| **`oauth4webapi`** (3.8.8, verified with `npm view`) is the Web OIDC client; **Auth.js / next-auth is not used** | Accepted | npm `latest` of `next-auth` is v4; v5 is still `5.0.0-beta.x`, which violates the latest-stable policy, and it would duplicate our session/refresh layer (httpOnly cookies, single-flight refresh, `proxy.ts` guard, BFF). `oauth4webapi` is zero-dependency, OpenID-certified and is what Auth.js itself builds on | Auth.js v5 is stable **and** supports Next 16 **and** covers our refresh needs (rotation, single-flight, reuse window, definitive-rejection semantics) |
