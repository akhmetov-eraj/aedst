# i18n — per-module translations across all four platforms

**Mandatory rule:** translations live next to the feature/module that owns
them — never in one global catalog. This is the same module-boundary
philosophy [library-first.md](/library-first) applies to code, applied to
strings: a module's translations are part of that module, and adding a
module means adding its own translation files, not editing a shared
mega-file. All four client platforms follow this now; the mechanism differs
per platform because each uses its own platform-native i18n system (per
[library-first.md](/library-first): platform API before custom code — no
hand-rolled translation loader anywhere in this repo).

## Locales

Five locales everywhere: `ar` (Arabic), `en` (English), `ru` (Russian, the
project's default/source locale), and Tajik + Uzbek. **Locale code caveat**:
Web's directory name for Tajik is `tj`; Android/Apple/Desktop use the
ISO-639-1/BCP-47 code their platform actually expects, `tg`. This is not an
inconsistency to fix — it's each platform's own correct convention — but
know the mapping (`tj` directory on web ↔ `tg` locale everywhere else) when
porting a string.

## Mechanism per platform

| Platform | Mechanism | Where | Why this and not a library |
|---|---|---|---|
| Web | [next-intl](https://next-intl.dev) JSON, one file per locale per module | `src/modules/<name>/i18n/{ar,en,ru,tj,uz}.json`, plus `src/app/config/i18n/common/*.json` for app-shell strings | Approved stack pick in library-first.md; already the parity source of truth. |
| Android | Android resource qualifiers — per-module `res/values*/strings.xml` | `feature/<name>/src/main/res/values{,-en,-ar,-tg,-uz}/strings.xml`, `app/src/main/res/values*/strings.xml` for app-shell strings | This **is** the platform API (Android's own resource-merging system resolves strings by name across every module at build time) — no third-party i18n library needed. |
| Apple | Xcode **String Catalog** (`.xcstrings`), one per SwiftPM target | `Features/<Name>/Sources/<Name>/Resources/Localizable.xcstrings` | Native since Xcode 15 (this repo targets iOS 17/macOS 14, already inside that floor) — holds every locale in one JSON file per target, no per-locale `.lproj` folders to keep in sync by hand. |
| Desktop | Qt Linguist (`.ts` source + CMake `qt_add_translations()` → `.qm`) | `Modules/Features/<Name>/i18n/<name>_<locale>.ts` | Qt's own i18n toolchain (`lupdate`/`lrelease`); QML strings wrapped in `qsTr(...)`, C++ strings in `QObject::tr(...)`/`QCoreApplication::translate(...)`. |

## Cross-platform content consistency

Web's existing 5-locale JSON is the single source of truth for copy — every
other platform's translation was ported key-for-key from it, not
re-translated independently, so all four platforms say the same thing per
locale. When adding a new user-facing string on any platform, port it the
same way: write the copy once (in whichever platform needs it first),
translate it into all 5 locales, then carry the exact same 5 strings into
the other platforms' catalogs as their features reach that screen.

| Auth | ✅ `modules/auth/i18n` | ✅ `feature/auth` (`auth_*` keys, wired into `LoginScreen.kt`) | ✅ `Features/Auth` (`authLogin*` keys, wired into `LoginView.swift`) | ✅ `Modules/Features/Auth/i18n` (`LoginView` context, wired via `qsTr`) |
| Home | ✅ `modules/home/i18n` | not built natively yet | not built natively yet | not built natively yet |
| Tasks | ✅ `modules/tasks/i18n` | not built natively yet | not built natively yet | not built natively yet |

Only the auth screen's *rendered* fields were localized on each native
platform (matching what each `LoginView`/`LoginScreen` actually shows today)
— register/sign-out copy exists in Web's catalog and should be ported to a
platform only once that platform builds the corresponding UI, per
[library-first.md](/library-first)'s "don't build ahead of an actual
requirement." As `feature/tasks`/`Features/Tasks`/`Modules/Features/Tasks`
get built on each native client (see each platform's architecture doc), they
each get their own `i18n`/`Resources`/`Localizable.xcstrings` following the
exact pattern above — never added to `auth`'s or the app-shell's catalog.
