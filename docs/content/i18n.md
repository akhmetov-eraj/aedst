# i18n overview — per-module translations across all platforms

**Mandatory rule:** translations live next to the feature/module that owns
them, never in one global catalog. This is the module-boundary philosophy of
[library-first](/library-first) applied to strings: a module's translations are
part of that module, and adding a module means adding its own translation
files, not editing a shared mega-file. All four client platforms follow this;
the mechanism differs per platform because each uses its own platform-native
i18n system (platform API before custom code: no hand-rolled translation loader
anywhere in this repo).

## Locales and the `tj` / `tg` convention

Five locales everywhere: `en` (English, the reference locale for parity and the
**web default**: `defaultLocale` in `apps/web/src/shared/i18n/locales.ts`), `ru`
(Russian, the source locale of Android's unqualified `values/`, declared with `unqualifiedResLocale=ru` in each app's `res/resources.properties` so the generated locale config lists it), `tg` (Tajik),
`uz` (Uzbek) and `ar` (Arabic, right-to-left).

**Tajik code convention.** The canonical code is `tg` (ISO 639-1/BCP-47). The
only platform that uses `tj` is **Web**, as its internal locale identifier
(`locales.ts`, the `[locale]` URL segment, `i18n/tj.json` files); `tj` is
Tajikistan's country code and was kept on web to avoid renaming. Web converts
it to the real BCP 47 tag `tg` for `<html lang>`, `hreflang`, `og:locale` and
JSON-LD (`toLanguageTag`). Android (`values-tg`), Apple (`tg` in `.xcstrings`)
and Desktop (`*_tg.ts`) use `tg`. Rule: write `tg` in new docs, tooling and
native code; use `tj` only inside web. `scripts/check-i18n-parity.mjs` normalizes
`tj` to `tg` internally.

## Mechanism per platform

| Platform | Mechanism | Where | Why this and not a library |
|---|---|---|---|
| [Web](/web/i18n) | [next-intl](https://next-intl.dev) JSON, one file per locale per module | `src/modules/<name>/i18n/{ar,en,ru,tj,uz}.json`, plus `src/app/config/i18n/common/*.json` for app-shell strings | Approved stack pick in library-first. |
| [Android](/android/i18n) | Android resource qualifiers: per-module `res/values*/strings.xml`. The unqualified `values/` is the default locale, **Russian**; `values-en`, `-tg`, `-uz`, `-ar` hold the rest | `feature/<name>/src/main/res/values{,-en,-ar,-tg,-uz}/strings.xml`, `app/` and `core/*/` for shared strings | This **is** the platform API; Android merges resources by name across modules at build time. |
| [Apple](/apple/i18n) | Xcode **String Catalog** (`.xcstrings`), one per SwiftPM target | `Features/<Name>/Sources/<Name>/Resources/Localizable.xcstrings` | Native since Xcode 15 (the repo targets iOS 18 / macOS 15); all locales in one JSON file per target. |
| [Desktop](/desktop/i18n) | Qt Linguist (`.ts` source + CMake `qt_add_translations()` producing `.qm`) | `Modules/Features/<Name>/i18n/<name>_<locale>.ts`, `App/i18n/`, `Modules/Core/DesignSystem/i18n/` | Qt's own toolchain (`lupdate`/`lrelease`); `qsTr(...)` in QML, `QObject::tr(...)` in C++. The English source text is the key. |

## Cross-platform content consistency and key mapping

Web's JSON is the reference copy. Native platforms port key-for-key from it
when their feature reaches that screen, so all platforms say the same thing per
locale. When adding a user-facing string, write the copy once, translate it
into all 5 locales, and carry the same 5 strings into the other platforms'
catalogs as their features reach that screen.

Key-mapping convention, used by the parity script's `--cross` report:

| Platform | Key shape | Example |
|---|---|---|
| Web | `<module>.<section>.<key>` (module = i18n directory owner; `common` for app-shell) | `auth.login.title` |
| Android | `<module>_<section>_<key>` (snake_case, module-prefixed) | `auth_login_title` |
| Apple | `<module><Section><Key>` (lowerCamelCase, module-prefixed) | `authLoginTitle` |
| Desktop | Qt context + English source text (not comparable by name) | `LoginView::Sign in` |

All three of the first rows normalize to the same lowercase `[a-z0-9]` string.

## Parity check

`scripts/check-i18n-parity.mjs` (`task check:i18n`, also a CI job in
`policies-ci.yml`):

- Within each platform, each bundle (web `i18n` directory, Android module
  `res/`, Apple `.xcstrings`, Desktop `.ts` family) must have the same keys in
  `en`, `ru`, `tg`, `uz`, `ar`, with the same placeholders (`{name}` ICU args on
  web, `%1$s` / `%d` on Android, `%@` / `%lld` on Apple, `%1` / `%n` on
  Desktop). Reports missing keys, extra keys, placeholder mismatches and absent
  locale files. Exit code 1 on any finding.
- Desktop: a translation that is empty or marked `unfinished` counts as missing.
- `--cross` additionally lists logical keys present on some of web / Android /
  Apple but not all (informational; `--strict-cross` makes it fail). Many web
  keys are legitimately web-only (admin console), so this report is a worklist,
  not a gate.
- `scripts/i18n-parity.allowlist` lists intentional exceptions, one per line,
  each with a reason. Do not use it to hide a translation gap.

Last run (2026-10-09, working tree): Web, Android and Apple had no per-platform
gaps. Desktop now has all five catalogs complete for all eight modules (203 source
strings; the earlier gap, with `admin`, `media`, `notifications` and `search` at
zero messages and `tasks`/`app` partly empty, is closed), with real plural forms
for every `%n` string (ru 3, ar 6, uz/tg/en 2). The Android TV app (`app-tv`) ships
the default Russian `values/` only, which is allowlisted.

Desktop has two extra gates (`apps/desktop/scripts/`): `check-i18n-extract.mjs` (no Qt
needed: every `qsTr()/tr()` source string must be in all five catalogs, translated, with
numerus forms for `%n`; the shrink-only baseline `i18n-baseline.json` is now empty) and
`check-i18n-lupdate.sh` (CI, with Qt: `lupdate -no-obsolete` in a temporary copy must find
nothing the catalogs lack). The catalogs were regenerated by a script from the sources
because `lupdate` was not available: run the `update_<module>_translations` targets once
with Qt installed and commit any difference lupdate makes (contexts, `<location>` lines).
Qt's own strings (standard dialog buttons, QML Controls) come from `qtbase_<lang>.qm` and
`qtdeclarative_<lang>.qm`, which `TranslationLoader` loads from the deployed `translations/`
folder or the Qt installation when Qt ships them for that language.

"yes" means the catalog files exist for the module; coverage of every screen's

module on a native client gets its own `i18n` / `Resources` /
`Localizable.xcstrings`, never added to another module's catalog. Android
and Apple compile only after their first real build (see
[Platform status](/status)); the i18n files themselves are plain data.
